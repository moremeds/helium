## 0. 现状（代码事实）

- `plugins/delivery-email/src/channel.ts` 用 **nodemailer 9.0.5**（已在 root 和 plugin 的
  `package.json` 里）。当前 `sendMail` 只传 `{ from, to, subject, text }` —— **没有 `html`，

- `DeliveryPayload = { tenant, runId, subject, body, artifacts?: string[] }`，`artifacts`
  的注释已经写着 "Absolute paths of files the channel **may attach or reference**" ——
  CID 内嵌图片这条路在类型层面已经预留好了。[COMPUTED, HIGH]

  没有任何模板引擎、没有 juice/mjml/sharp/canvas。[COMPUTED, HIGH]
- nodemailer 原生支持 `html` 字段与 `attachments: [{ filename, path|content, cid }]`，
  CID 引用写作 `<img src="cid:xxx">`。**零新依赖即可发富 HTML + 内嵌图。**[KNOWN, HIGH]

## 1. 2026 年 HTML 邮件约束（数据来自 caniemail.com API）

我直接拉了 `https://www.caniemail.com/api/data.json` 逐特性核对，以下是硬数据而非记忆。
[COMPUTED, HIGH]

| 特性                                | Apple Mail iOS       | Gmail web               | Gmail iOS             | Gmail Android | Outlook.com/iOS              |
| ----------------------------------- | -------------------- | ----------------------- | --------------------- | ------------- | ---------------------------- |
| `<table>`                           | y                    | y                       | y                     | y             | y                            |
| `width` / `max-width`               | y                    | y                       | y                     | y             | y                            |
| `border-radius`                     | y                    | y                       | y                     | y             | y                            |
| `background-image`                  | y                    | y                       | y                     | y             | y（Win 桌面版 n）            |
| `display:flex`                      | y                    | y                       | **a**（部分）         | **a**（部分） | y                            |
| `box-shadow`                        | y                    | **n**                   | a                     | a             | 2023-12 起 y                 |
| `position`                          | 仅 relative/absolute | **n**                   | **n**                 | **n**         | 部分                         |
| `@media`                            | y                    | y                       | y                     | y             | y                            |
| **`@media (prefers-color-scheme)`** | **y**（iOS 13+）     | **n**                   | **n**                 | **n**         | **y**（带 `data-ogsc` 变体） |
| `color-scheme` CSS 属性             | y（仅 html 根）      | **n**                   | **n**                 | **n**         | **n**                        |
| `<meta name="color-scheme">`        | macOS y / **iOS n**  | **n**                   | **n**                 | **n**         | **n**                        |
| **内嵌 `<svg>`**                    | **y**                | **n**                   | **n**                 | **n**         | **n**（全线）                |
| `<img src="*.svg">`                 | iOS 15+ y            | **n**                   | a（仅非 Google 账号） | a（同上）     | y                            |
| **base64 / data URI 图**            | **y**                | **n**                   | **n**                 | **n**         | y                            |
| `<picture>`                         | y                    | **n**（被替换成 `<u>`） | n                     | n             | n                            |

结论（全部 [COMPUTED, HIGH]）：

1. **布局必须 table-based**。`position` 在 Gmail 全线不支持，`flex` 在 Gmail App 上只是
   partial，`<picture>` 被 Gmail 直接改写成 `<u>`。唯一 100% 安全的排版原语是嵌套
   `<table>` + `width` 百分比/像素 + `align`。
2. **样式必须内联 + 一个 `<style>` 兜底**。Gmail 自 2016 起支持 `<head><style>`，但
   `@media` 在 Yahoo 是 `_filtered_` 掉的，Gmail 只对非 Google 账号有额外坑
   （caniemail note #6："Not supported with non Google accounts"）。所以：**基础样式内联，
   `<style>` 里只放 media query 覆盖**。
3. **宽度 600px 上限**，外层 `max-width:600px;width:100%`，手机断点 ≤360px 再堆叠。
   （原型里我把断点从 420 调到 359，因为 iPhone 15 是 390pt，420 的断点会把两栏
   行情条和三栏盈亏格全拆成单栏，白白拉长两屏。[COMPUTED]）
4. **`prefers-color-scheme` 对 Gmail 完全无效**（web/iOS/Android 全 n）。Gmail 自己做
   颜色反转：**iOS 上是 full invert，Android 上是 partial invert**
   （[Dyspatch](https://www.dyspatch.io/blog/the-danger-of-dark-mode-and-email/)、
   [Enchant](https://www.enchantagency.com/blog/dark-mode-email-design-best-practices-css-guide-2026)）。
   [KNOWN, MED——两篇二手来源一致，无一手 Google 文档]
5. Outlook.com / Outlook iOS 在暗色模式下**不走 media query 而是往 DOM 上加
   `data-ogsc` / `data-ogsb` 属性**（caniemail note #3，指向
   [hteumeuleu 的分析](https://www.hteumeuleu.com/2021/emails-react-outlook-com-dark-mode/)）。
   所以暗色兜底要写三份：`@media (prefers-color-scheme:dark)`（Apple）、
   `[data-ogsc]` 选择器（Outlook）、以及**颜色本身要抗反转**（Gmail）。

**抗反转的实操规则** [INFERRED, MED]：不要用纯 `#ffffff` 背景配纯 `#000000` 文字——
full invert 会把它变成纯黑配纯白，刺眼且丢层级；用 `#ffffff` 卡片 + `#eef0f4` 页底

- `#161a20` 文字这种"接近但不到极值"的中间调，反转后仍然保有层级差。彩色语义标签
  （绿/红/琥珀）用**中饱和度**而非荧光色，反转后不会变成不可读的荧光。并且
  **颜色永远不是唯一信号**——原型里每个 chip 都带文字（BULLISH / BEARISH / NEUTRAL）。

**字体**：不要引 web font（Gmail 剥离 `@font-face`）。用系统栈
`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, Helvetica, Arial, sans-serif`，
数字/表格用 `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace`。`rem` 在 Yahoo
是 n（caniemail），所以**全部用 px**。[COMPUTED, HIGH]

## 2. 图表：四条路的取舍

| 方案                                    | iOS Mail | Gmail App                     | 判决                   |
| --------------------------------------- | -------- | ----------------------------- | ---------------------- |
| (a) 内嵌 `<svg>`                        | ✅       | ❌ 元素连同 fallback 一起被删 | **淘汰**               |
| (b1) PNG 走 data URI                    | ✅       | ❌ `src` 被改写成 `nosrc`     | **淘汰**               |
| (b2) PNG 走 CID 附件                    | ✅       | ✅                            | **可用**，但需要生成器 |
| (c) 纯 HTML/CSS 条（table cell 背景色） | ✅       | ✅                            | **首选**               |
| (d) Unicode sparkline `▁▂▃▅▇`           | ✅       | ✅                            | **可用**，零成本       |

注意 (b1) 这条是最容易踩的坑：caniemail `image-base64` 对 Gmail 四个渠道全是 `n`，
note #2 明确写 "Not supported. The `src` is turned into a `nosrc` attribute."
—— **data URI 在 Gmail 上是彻底不显示，不是降级。**[COMPUTED, HIGH]

**逐图表建议**（按"能用 CSS 就别生图"排序）：

| 图                        | 建议                                              | 理由                                                         |
| ------------------------- | ------------------------------------------------- | ------------------------------------------------------------ |
| IV rank gauge             | **(c) 两个 `<td>` 的宽度百分比**                  | 就是一根进度条，一行 HTML                                    |
| Gamma level bar（发散条） | **(c) 三列表格：标签 / 右对齐负向 / 左对齐正向**  | 原型里已经跑通                                               |
| Levels ladder             | **(c) 每行一个 4px 色条 `<td>` + 单空格字体数字** | 本质是表格不是图                                             |
| 风险/收益比例条           | **(c)**                                           | 同上                                                         |
| SPX/VIX sparkline         | **(d) Unicode 起步，(b2) CID PNG 作为升级**       | 8 段 blockchar 已经能表达"压/涨"；真要 60 点日内曲线再上 PNG |

**关于 PNG 生成（ponytail 规则）**：不需要 sharp / canvas / resvg / pngjs。PNG 的最小
可用编码就是 `签名 + IHDR + IDAT(zlib deflate 的扫描线，每行前缀一个 filter byte 0) + IEND`，
每个 chunk 带 CRC32。我在 scratchpad 写了一个 **40 行、只用 `node:zlib` 的编码器**并
实际跑通：300×60 的 sparkline，**输出 425 字节，`file` 确认是合法 PNG**。
[COMPUTED, HIGH —— 见 `scratchpad/png.mjs` 与 `scratchpad/spark-test.png`]

所以结论是：**先不生图**（阶段一纯 CSS + Unicode 就够）；**如果之后要真曲线，用那 40 行
自制编码器 + nodemailer CID 附件，仍然零新依赖。**pngjs 虽然"no dependencies"，但
它引入的是一个完整的编解码器，我们只需要单向、单色深、无 filter 的那 5%。

## 3. 三份金融日报的排版可借鉴处

1. **Morning Brew** —— 结构是 "eyebrow / headline / image / prose" 的三段式卡片，
   靠 **1px `#e6e6e6` 边框 + 15px 圆角（仅顶部两角）+ 15px 左右内边距**把三段拼成一个视觉
   整体；他们明确指出这么拆是因为 **"Gmail 和大多数客户端不支持负 margin"**
   （[newsletterexamples.co 拆解](https://www.newsletterexamples.co/p/want-to-design-a-morning-brew-style-email-here-s-a-cheat-sheet)）。
   → 借鉴：**卡片化 + 边框而非阴影**（box-shadow 在 Gmail web 是 n）。原型照做了。
2. **Axios（Smart Brevity）** —— 四件套：≤6 词的标题 tease、一句 lede、**加粗的
   "Why it matters"**、"Go deeper" 链接；靠加粗 lead-in + 项目符号做扫读
   （[Axios HQ](https://www.axioshq.com/research/smart-brevity-communication-checklist)、
   [Axios 自述](https://www.axios.com/2022/09/23/our-secret-sauce-for-better-communication-axios-smart-brevity)）。
   → 借鉴：原型顶部的 **"Verdict:" 加粗 lead-in 一句话**，就是 "Why it matters"
   的位置；底部 "What kills this view" 是反向的同一手法。
3. **Sherwood / Robinhood Snacks** —— 定位是"零售投资者、低时间投入、不端着的语气"
   （[Readless](https://www.readless.app/blog/best-finance-newsletters-2026)）。
   → 借鉴：**信息密度必须在一屏内给出结论**，细节往下沉。原型的顺序
   （regime badge → 一句话 verdict → 行情条 → 日历 → 关卡 → 候选单）就是这个梯度。
   [INFERRED, MED —— 这条是我从定位推的排序原则，不是他们公开的规范]

共同的移动端技巧：单栏为主、两栏只在"对称的一对数字"时用、分节靠**卡片间距而非分割线**、
时间/数字列固定宽度 + 等宽字体。

## 4. 给 helium 的推荐方案

**库选择：不加任何依赖。** [推荐, HIGH]

- 模板：`plugins/delivery-email/src/template.ts`，纯 template literal 函数
  `renderBrief(data): string`。不引 mjml（要构建步骤）、不引 juice（我们本来就手写内联样式）。
- 渲染管线：tenant 产出结构化 `brief` 对象 → `renderBrief()` 出 HTML →
  `channel.deliver` 同时传 `text`（现有 markdown，作为 fallback，**必须保留**）和 `html`。
  nodemailer 会自动组 `multipart/alternative`。
- `DeliveryPayload` 加一个可选 `html?: string`（或 `bodyHtml`），保持 `body` 为纯文本。
  这样 `delivery-markdown` 通道完全不受影响。
- 图表：阶段一全部 CSS/Unicode，**不生成任何图片**，邮件是纯文本 HTML，体积 <60KB。
  （Gmail 在 102KB 后会截断并显示 "View entire message" —— [KNOWN, MED]，未在本次核实，
  但是长期存在的门槛，值得作为预算上限。）
- 暗色策略：三层。① 内联的浅色基础样式用中间调，抗 Gmail 反转；
  ② `<style>` 里 `@media (prefers-color-scheme: dark)` 覆盖 `.card/.ink/.rule/.track`
  给 Apple Mail；③ `[data-ogsc] .ink{}` 给 Outlook.com。**不要**只靠 ②。

**落地顺序建议**：先只做 HTML（第一版），跑一周看 iOS Mail + Gmail App 的实际观感，
再决定要不要上 CID PNG。这符合 doctrine 6（ceremony must earn its keep）。

## 5. 陷阱清单

1. **data URI 图在 Gmail 全线不显示**（`src`→`nosrc`）。想内嵌图只能 CID 附件。
2. **内嵌 SVG 在 Gmail/Outlook 被整个删掉，连 fallback 内容一起删**——不能靠 fallback。
3. **`prefers-color-scheme` 在 Gmail 无效**，Outlook 走 `data-ogsc` 属性而不是 media query。
4. **`<meta name="color-scheme">` 在 iOS Mail 是 n**（只有 macOS 支持），别指望它挡住反转。
5. **`box-shadow` 在 Gmail web 不支持** → 卡片用 1px border，不用阴影。
6. **`rem` 在 Yahoo 不支持** → 全 px。
7. **`position` 在 Gmail 全 n** → 不要做浮层、角标叠加。
8. **`<picture>` 被 Gmail 换成 `<u>`** → 不要用它做明暗双图。
9. **必须保留纯文本 `text` part**：现在的 markdown 是唯一 body，换成 html-only 会让
   纯文本客户端和某些反垃圾评分变差。
10. **CID 附件会让邮件"带附件"** ——某些客户端会在列表里显示回形针图标，且
    `artifacts` 现在是被拼进 text 的路径字符串，改成附件时要小心不要把本地绝对路径
    泄露进邮件正文。
11. **邮件体积**：base64 附件膨胀 33%，多张 PNG 很容易越过 Gmail 的截断阈值。
12. **每日限额逻辑不变**：`maxPerDay` 计数在 `sendMail` 成功后才 +1，加 html 不影响，
    但**渲染失败必须降级回纯文本发送，而不是抛异常吃掉当天配额**。[INFERRED, HIGH]
13. **preheader**：原型里放了隐藏 preheader（收件箱预览行）。必须补足空白字符，
    否则客户端会把正文首句拉进来。
14. Playwright 只能证明"在 Chromium 里对"，**证明不了 iOS Mail / Gmail 的渲染**。
    真正验收要么用 Litmus/Email on Acid，要么给自己发一封实测。[KNOWN, HIGH]

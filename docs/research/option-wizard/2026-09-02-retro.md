## 0. 最短结论

**根因不在提示词，在于「谁负责渲染报告」这件事从来没人做。** [INFERRED, HIGH]

spec §2 写着 render+deliver 是 "deterministic template over the accepted
proposals + gate records"。但 doctrine 2 禁止 core 认识期权，于是
`packages/cli/src/runner.ts::deliveryBody()` 只能写一个**通用的 run 逐步转录**：
按 step 顺序打印 `## <task> — <role>`，把每个 agent 的**原始文本**原样贴进去
（`summariseToolLines` 只折叠 `name -> payload` 行，其余"role's own writing
passes through untouched"）。tenant 侧没有任何 renderer。所以读者拿到的不是晨报，
是**四个 agent 的思考过程存档**。

第二根因：**旧 skill 的领域知识（VRP 三档、regime×structure 矩阵、30-45 DTE、
21 DTE、5% NLV 分级、四信号 veto、pitfall 07 盘前 UW 冻结）一条都没进 team.yaml
的 persona**。persona 里 90% 的字数在讲"不要编造 strike"和"输出必须是纯 JSON"——
全是**过去事故的补丁**，没有一句交易学。

## A. 现有报告解剖：为什么读不下去

6 份报告：3 成功（`3a1b395b` 14.7K、`84a83ad2` 22.9K、`ad9c67bc` 10.5K）、
3 失败（894B–2.5K）。结构固定为：标题 → Outcome → 缺陷清单 → 4 个 step 段
→ `helium audit <run>` 尾巴。

**A1. 头部：三行「tool unconfigured」，而且是假的。** [COMPUTED, HIGH]
三份成功报告都以这三行开场：

> `- **tool unconfigured:** ow_tv_watchlist (OW_TV_ENABLED unset)`
> `- **tool unconfigured:** ow_spot (OW_TV_ENABLED unset)`

但 `tools/index.ts:35-40` 的注释明确说这是**误报**："naming OW_TV_ENABLED here
made the run report reads them as broken on the very machine they were made to
work on"。`ow_spot` 有 UW 回退路径，`ad9c67bc` 的 designer 确实拿到了
SPY 762 / QQQ 706.85 / NVDA 217.94。**报告头部宣布工具坏了，正文却在用它们的输出。**
读者第一眼读到的三行是错的，这直接摧毁对下面所有数字的信任。

**A2. universe 段：三行 IO 噪音，零信息。**

> `- ow_tv_watchlist — ok, 1177 bytes`
> `ow_spot: skipped, needs parameters this step cannot supply`

"1177 bytes" 对交易员没有任何意义。选出了哪些票、多少只、来自 TV 还是
OW_UNIVERSE 兜底——**一个都没写**。

**A3. regime 段：唯一可读的部分。** opus 写的，有日期、有数字、有 staleness 标注。
但它是 4-5 段**没有小标题的密排散文**，手机上是一堵墙；而且每段结尾都在道歉
（"argon macro lag: DTWEXBGS 5 days behind…"）。

**A4. design 段：赤裸的 JSON dump + 模型的自言自语。** 这是崩塌点。
`84a83ad2` 的 design 段里，模型**连续吐了三个完整 JSON 方案**，中间夹着：

> `Actually, let me simplify and focus on the highest-conviction plays with real bid/ask data:`
> `Let me refine once more with real data:`

三份方案全部原样进了邮件（约 8KB）。读者要自己判断哪一份算数。另外两份的开场白同样入镜：
`Perfect. Now I have all the data I need.` / `Based on all the data, I'll now construct my proposals:`。

**A5. review 段：把 design 段整个复制一遍。** risk-reviewer 的协议是"输出保留的
proposals，同样的 shape"，于是 5 条提案的完整 JSON（含 rationale 全文）**第二次**
出现在同一封邮件里。`ad9c67bc` 的 review 段是 pretty-print 的 JSON，占报告 60%。
`runner.ts:892` 的 `summariseToolLines` 检测到裸 JSON 就加 ```json 围栏——
**它把 JSON 渲染得更整齐了，但没有把它变成人话。**

**A6. 缺失的东西比存在的更致命。**
没有 spot 与 strike 的并排对照、没有 max loss / max gain / breakeven 表、
没有到期天数、没有 bid-ask 与 OI（`ow_uw_chain` 明明返回了 NBBO 和 OI）、

**refusal**，不打印 verdict。读者收到 5 条"通过了 preflight"的提案，
**永远不知道其中 4 项风控根本没跑过**。

## B. 推理质量：不客气地说

**B1. Regime 判断本身是合格的。** [INFERRED, MED]
三次都得出"risk-off / 低但走高的 vol / 保留对冲"，引用了 DGS10 4.75、DFII10 2.44、
VIXCLS 14.92、HY OAS 2.63，并标注了 2 天/5 天滞后。没有发现幻觉数字，内部无矛盾。
`84a83ad2` 拿到 TV live 后给出 2y 4.371 / 5y 4.532 / 10y 4.772 / 30y 5.245 / VIX 16.02 /
DXY 99.719——曲线形状自洽。**但**同一个早上，三份报告对 VIX 的说法分别是
"14.92（8/31）"和"16.02（live）"，差 7%，读者收到六封邮件会看到两个互相矛盾的世界。

**B2. Structure 设计有系统性算术错误。这是致命的。** [COMPUTED, HIGH]

- **买低卖高的 put 被标成 "put debit spread"，方向完全反了。** `84a83ad2`：
  > SPY `buy 740P / sell 750P`, `"strategy":"put_debit_spread_hedge"`, `limitPrice: 3.80`,
  > rationale: `"Net ~$1.28 credit per spread"`

  买 740 卖 750 是**净收权利金的 bull put spread**，SPY 涨或横盘才赚。它被当作
  "risk-off 环境下的下行对冲"卖给读者。TLT `buy 80P / sell 81P` 同样反向。
  **两条在"跌"的判断下会在跌的时候亏钱的仓位，通过了 review 进了最终 5 条。**
- **limitPrice 与 rationale 自相矛盾。** 上面这条 rationale 自报 $1.28 **credit**，
  字段却写 `+3.80`（`ow_ib_preflight` 定义 `Net debit(+) / credit(-)`）。
  QQQ 报 `9.57 − 6.26 = 3.31 debit`，字段写 `5.75`（高 74%）。IWM 报 2.01，字段 3.40。
  GLD 报 2.28，字段 2.60。**五条里没有一条的 limitPrice 与自己的推理一致。**
- **debit spread 的 max loss 被算成了 max gain，连错六次。** `3a1b395b`：
  > `"Risk defined at width minus premium (24 – 2.35 = 21.65 max loss per spread)"`

  买入价差的最大亏损**就是付出的权利金 2.35**，21.65 是最大收益。SPY/QQQ/IWM/TLT/
  XLV/XLP 六条全部同样写反。同一份报告里的 credit spread（785/800，"15 − 0.38 = 14.62"）
  却是对的——说明模型把 credit spread 的公式无差别套到了 debit spread 上。
- **`ad9c67bc` 的 SPY**：`limitPrice 2.50` 却写 `"caps risk to ~$50/contract
  ($250 total max loss on 5x)"`。差 5 倍（真实为 $250/张、$1,250 总额）。

**B3. risk-reviewer 的唯一职责是算术，它算错了。** [COMPUTED, HIGH]
`84a83ad2` 的 reviewer 声称：

> `**IWM (spot 290.57):** Put spread (buy 285, sell 275): Both strikes are 5.3–5.5% below spot. ✓`

285 距 290.57 是 **−1.92%**，不是 5.3%。GLD 385 距 396.75 是 **−2.96%**，它写 5.4%。
两处错误方向一致：**把贴近平值的 strike 说成远离平值**，正好掩盖它该抓的问题。
同时它对 B2 的所有 debit/credit 方向错误、limitPrice 错误、max-loss 错误
**一个都没发现**——它只做了"strike 是否离 spot 太远"这一项检查。

**B4. 结构与 regime 打架。** `ad9c67bc` 的 regime 说"vol 被低估，要买 vol 不要卖"，
design 却给了 NVDA、TSLA 两条 call credit spread（卖 vol）。TSLA 卖 360 call、
spot 357.5、自称 "0.45 delta"——在"risk-off"书里卖近乎平值的 call，收 $0.62 赌
$9.38，**风险报酬 1:15**，reviewer 全部放行。`3a1b395b` 的 reviewer 反倒抓到了
同一矛盾并剔除了两条 call spread——**同一个 haiku 模型，同一天，行为不可复现。**

**B5. 无幻觉 strike，但有幻觉精度。** 没再出现 QQQ 420/410 这种事故（`ow_spot` 前置
生效了）。但 "delta -0.249"、"ask $5.14" 这类数字没有一处标注来源与时间戳，
读者无法区分哪些来自 `ow_uw_chain` 的真实 NBBO、哪些是模型顺手编的。

## E. 教训、反模式、新晨报骨架

### E1. 反模式

1. **"报告 = run 转录"**。deterministic renderer 被 doctrine 2 挤到了 core 里，
   core 不懂期权，于是没人写 renderer。**tenant 必须自带 renderer**——它是 tenant 的
   领域知识，本来就该在 `plugins/option-wizard/` 里。
2. **让模型直接输出面向人的文本**。design/review 的原始 stdout 进邮件，"Actually, let
   me simplify" 也就进了邮件。**agent 输出结构化数据，渲染由确定性代码做。**
3. **persona 全是事故补丁，没有交易学**。structure-designer 的 persona 有 27 行，
   讲 QQQ 420/410 事故的占 8 行，讲 IB 502 的占 3 行，**讲如何选结构的：0 行**。
4. **审阅者只查一件事，还查错了**。把 review 定义成"算术检查"，它就只做算术，
   而且 haiku 做不对。**算术应该是确定性代码算的，review 应该判断的是"这笔交易该不该做"。**
5. **风控门静默 unchecked**。4/5 子门因为 `extensions:{}` 永远不裁决，报告还不显示。
   **一个不显示自己没跑的门，比没有门更危险。**
6. **同一天六封邮件，三份成功报告互相矛盾**。cron 重试没有幂等/去重。
7. **无记忆**。没有昨日提案、没有 ledger、没有 regime 历史——**无法学习，也无法被验证。**
8. **失败报告只讲 env var，不讲市场**。三份失败报告读者收到的是运维日志。
   晨报失败时应该说"今天没有可交易的结论，原因：X"，而不是 `CODEX_ACCESS_TOKEN is unset`。

### E2. 新晨报目标骨架（手机阅读，期权导向，定义风险）

固定 8 节，**全中文，英文术语保留**，整篇目标 < 800 字，超出的进折叠/附录：

```
# 美股晨报 2026-09-02（周三，盘前 06:00 ET）

## 0. 一句话                       ← 今天做什么 / 不做什么，一行
## 1. 昨日未结                     ← ledger：上次说要 roll/close 的事，今天到期没有
## 2. 盘面                         ← 3-5 个数字：ES 隔夜、VIX(live)、10y、DXY，各带时间戳
##    今日日历                     ← 经济数据 / 财报 / OPEX，只列 T+0 到 T+5
## 3. Regime 判定                  ← 三行：方向 / 波动率(RICH·NEUTRAL·CHEAP + VRP 数值) / 对冲姿态
##    反面论证                     ← 一行：这个判断最可能错在哪
## 4. 今日提案（≤3 条，按优先级）   ← 每条一张卡：
      TICKER  结构名  spot X → 腿 A/B  DTE n
      净借/贷 $x · 最大亏 $y · 最大赚 $z · 盈亏平衡 w
      仓位：tier(NORMAL) = q 张 = 2.4% NLV
      为什么：一句 · 失效条件：一句
      流动性：spread 3.2% of mid · OI 1,240/890 ✓
## 5. 已否决（≤3 条，一行一条）     ← ticker + 一句话原因
## 6. 持仓提醒                     ← 21 DTE 到期名单 / 集中度告警 / 定义风险审计
## 7. 数据完整性                   ← Layer Coverage 小表：每层 ✓/skipped + 来源 + 时效
##    本报告缺什么                 ← 明确列出，不藏
```

关键设计约束：
- **第 4 节的卡片必须由确定性代码渲染**，数字（max loss / max gain / breakeven /
  spread% / 仓位%）由代码从 legs + NBBO + NLV 算出，**模型只提供 legs 和一句 why**。
  B2 的六类算术错误全部由此消失。
- **提案 ≤3 而非 ≤5**。手机上 5 张卡要滑三屏；且当前 quantity 无 NLV 依据，
  先把 3 条做对。
- **第 7 节是 hard rule #8 的直接回归**——没有它，A1 那种"头部说工具坏了、
  正文却在用"的矛盾会一直存在。
- **失败时报告结构不变**，只是第 3、4 节写"数据不足，无结论"，把运维细节压到第 7 节。
